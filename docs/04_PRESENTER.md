1. Сделать презентацию и защиту на 4 минуты.
2. **Следить за временем команды и вовремя сдавать промежуточные решения.** Разработчики в коде

## Продуктовая рамка

Это то, что ты должен уметь сказать без слайдов.

**Пользователь.** Сотрудник, который написал в поддержку, и оператор первой
линии, через которого проходит весь поток. Помощник отвечает первому и
разгружает второго.

**Боль.** Обращения приходят почтой и звонками. Люди описывают проблему своими
словами, пропускают важные детали, задают три вопроса в одном письме. Оператор
каждый раз вручную вчитывается, достаёт логин и код ошибки, решает, куда это
отнести. Пока он разгребает очередь, человек ждёт.

**Решение.** SupportPilot разбирает обращение, находит ответ в базе знаний,
пишет его со ссылками на источники, **сам проверяет себя на выдумки** и
отправляет. Человек подключается только там, где проверка нашла замечание.

**Почему это не просто чат-бот.** Три отличия, которые надо назвать вслух.

1. Ответ собирается из конкретных фрагментов базы знаний, а не из памяти
   модели. Каждое утверждение несёт ссылку на источник.
2. Ответ проверяется до отправки, отдельной ролью с противоположной установкой:
   искать, за что зацепиться, а не защищать написанное.
3. Не прошедший проверку ответ не отправляется вовсе. Обращение уходит человеку.

**Почему человек не визирует каждый ответ.** Виза на каждом обращении —
это очередь, и выигрыш от скорости модели съедается ожиданием. Поэтому человек
разбирает исключения, а не поток. На нашей очереди из двенадцати обращений
девять уходят сами, три останавливаются.

## Структура презентации

Одиннадцать слайдов. На 4 минуты это предел, больше не успеешь.

| № | Слайд | Что на нём | Сколько говоришь |
|---|---|---|---|
| 1 | Титул | Название, тэглайн «ИИ-помощник первой линии поддержки», команда | 5 сек |
| 2 | Пользователь и боль | Один оператор, поток обращений, три цифры боли | 30 сек |
| 3 | Что делает продукт | Одна фраза и три иконки: разобрать, найти, выполнить | 20 сек |
| 4 | **Демо** | Живой прогон или видео | **90 сек** |
| 5 | Как устроен агент | Схема пяти шагов | 40 сек |
| 6 | Где LLM, а где код | Две колонки | 25 сек |
| 7 | Человек в контуре | Скриншот кнопок подтверждения | 15 сек |
| 8 | Эффект | Расчёт экономии | 20 сек |
| 9 | Стек и запуск | Логотипы, две команды запуска | 10 сек |
| 10 | Ограничения и планы | Честный список | 20 сек |
| 11 | Контакты и ссылки | QR на репозиторий | 5 сек |

Демо занимает почти половину времени. Так и должно быть: жюри хочет увидеть работающий продукт,
а не услышать про него.

### Слайд 2, цифры боли

Подавай их как оценку команды, а не как факт из отчёта. Формулировка: «по нашей оценке».

- Оператор тратит на разбор одного обращения около 6 минут.
- Примерно 4 из 10 обращений приходят с неполными данными, и по ним нужен ещё один круг переписки.
- Около трети обращений — повторы уже решённых проблем.

### Слайд 5, схема агента

```
[ Обращение ]
      |
  1. Модель: разобрать текст в структуру
      |
  2. Код: найти похожие заявки
  3. Код: найти фрагменты базы знаний (гибридный поиск)
      |
  4. Модель: выбрать действие
  5. Модель: написать ответ по фрагментам, со ссылками
      |
  6. Код + модель: проверить ответ на искажения
      |          не прошло -> переписать -> не прошло -> остановить
      |
  7. Код: выполнить действие
      |
   прошло проверку -> пользователю     есть замечание -> человеку
```

### Слайд 6, проверка на искажения

Это главный слайд. Два слоя, покажи оба.

**Код, миллисекунды, без модели.** Разрешаются ли ссылки. Откуда взялись числа,
коды ошибок, телефоны, адреса и сетевые пути. Не появились ли обещания сроков
и гарантий, которых нет в источниках.

**Модель, отдельным вызовом.** Разбор ответа на утверждения, по каждому вердикт:
подтверждается, противоречит, не найдено. Отдельно ищутся три типичных отказа:
склейка шагов из разных инструкций, распространение частного случая на общий,
подмена значений из источника.

Фраза для защиты: «Правдоподобность не является подтверждением. Общеизвестный
факт, которого нет в источниках, для нас такая же выдумка, как и любая другая».

### Слайд 7, где LLM, а где код

| Отдали модели | Оставили коду |
|---|---|
| Понять свободный текст на русском | Поиск по базе знаний, BM25 и векторы |
| Достать логин, код ошибки, устройство | Поиск похожих заявок |
| Определить категорию, приоритет, команду | Определение массового сбоя по счётчику |
| Выбрать следующий шаг | Проверка чисел, контактов и обещаний |
| Написать ответ по источникам | Создание записей и смена статусов |
| Сверить утверждения с источниками | Решение, отправлять или звать человека |

Фраза: «Мы сознательно не зовём модель там, где хватает двадцати строк кода.
Это быстрее, дешевле и предсказуемее. Половина проверки на галлюцинации —
обычные регулярные выражения, и они ловят самый опасный класс ошибок».

### Слайд 8, расчёт эффекта

Покажи формулу, а не голую цифру. Числа — это допущения команды, так и скажи.

```
Поток обращений на команду          120 в день
Ручной разбор одного обращения      6 минут
Разбор с помощником                 1,5 минуты (проверить и подтвердить)
Экономия на обращении               4,5 минуты
Экономия в день                     120 × 4,5 = 540 минут = 9 часов
В пересчёте на людей                примерно 1,8 ставки оператора
```

Обязательно добавь строчку: «Это оценка на наших допущениях, точные цифры зависят
от реального потока и доли сложных обращений». Жюри ценит честность гораздо выше красивой цифры.

### Слайд 10, ограничения и планы

Честный список выигрывает. Не прячь недостатки, жюри их всё равно найдёт.

**Ограничения прототипа**
- Локальный запуск, без развёртывания и без авторизации.
- Поиск похожих заявок по словам, без векторного поиска.
- База знаний из восьми статей, загружается из файла.
- Аудио звонков не обрабатываем, работаем с готовой расшифровкой.

**Что добавили бы дальше**
- Векторный поиск по всему архиву заявок вместо поиска по словам.
- Обучение на подтверждениях и правках оператора: чем чаще правят приоритет, тем точнее становится.
- Интеграция с реальной почтой и системой заявок.
- Автоматическое закрытие простых повторяющихся обращений после накопления статистики.

> **(0:00)** Добрый день. Мы сделали SupportPilot — ИИ-помощник технической
> поддержки, который проверяет сам себя, прежде чем ответить человеку.
>
> **(0:08)** Обращения приходят свободным текстом: человек пропускает логин,
> путает название сервиса, задаёт три вопроса в одном письме. Оператор
> разбирает это вручную, а пользователь всё это время ждёт.
>
> **(0:30)** Покажу, как это работает.
>
> **(0:40) ДЕМО.** Вот очередь. Беру письмо про VPN. Разбираю.
>
> Модель вернула структуру: суть, категория, приоритет с обоснованием, команда.
> Из текста вытащены логин, код ошибки и версия Windows.
>
> Дальше поиск нашёл четыре фрагмента базы знаний. Обратите внимание: два из них

> оно ссылается. Оценка 95 процентов. И смотрите на трассу: первый вариант ответа
> проверка отклонила, модель переписала его, второй прошёл.
>
> Ответ прошёл проверку, поэтому ушёл сразу. Человека не ждали.
>
> **(2:20)** Теперь обращение, где так не получилось. Критический приоритет,
> Wi-Fi лёг на целом этаже. Система остановилась и позвала человека.
> Здесь решение принимает он.
>
> **(2:45)** Модель работает на четырёх шагах из семи. Поиск, проверка чисел
> и контактов, подсчёт повторов — обычный код. Половина проверки
> на галлюцинации — это регулярные выражения, и они ловят самое опасное:
> выдуманный телефон, несуществующий срок, ссылку на источник, которого нет.
>
> **(3:15)** По нашим допущениям это экономит около девяти часов работы в день
> на команде, разбирающей сто двадцать обращений.
>
> **(3:35)** Ограничения. База знаний из двадцати статей, составленных нами:
> внутренние регламенты закрыты, и выдавать выдумку за них мы не стали.
> Дальше — векторный поиск по всему архиву заявок и обучение на правках оператора.
>
> **(3:55)** Спасибо. Развёрнуто, ссылка в презентации. Готов ответить на вопросы.

## Вопросы жюри и ответы

Подготовь их заранее, на них уходит вторая половина баллов.

**Вы отправляете ответы без человека. Что если модель ошибётся?**
Ответ отправляется только после проверки, которая сверяет каждое утверждение
с источником. Не прошедший проверку ответ не уходит вовсе: обращение
останавливается и ждёт человека. Критический приоритет тоже всегда идёт
к человеку. То есть человек не исчез, он перестал быть узким местом.

**Что если проверка сама ошибётся?**
Её первый слой — не модель, а код: проверка ссылок, чисел, контактов, обещаний.
Он даёт один и тот же результат при каждом запуске и не может «передумать».
Второй слой на модели добавляет полноты, но не отменяет первый.

**Что если модель ошибётся с приоритетом?**
Оператор видит обоснование приоритета и может поменять его в карточке.
Исправление сохраняется, и это данные, на которых систему можно донастроить.

**Почему не отдали модели весь процесс целиком?**
Модель дорогая, медленная и недетерминированная. Поиск похожих заявок и создание записи
в базе — это детерминированные задачи, код делает их за миллисекунды и всегда одинаково.
Модель нужна там, где есть неоднозначный человеческий текст.

**Как боретесь с придуманными фактами?**
Промпт прямо запрещает достраивать данные, отсутствующие поля просто не попадают в ответ.
Всё, чего не хватило, модель обязана перечислить отдельным списком, и именно он превращается
в уточняющие вопросы. Плюс человек подтверждает результат.

**Что будет на объёме в тысячи заявок?**
Поиск по словам придётся заменить на векторный, это основной пункт наших планов.
Остальная архитектура не меняется: это обычное приложение с базой.

**Сколько стоит и сколько занимает один разбор?**
От двух до четырёх вызовов модели, в среднем 4,5 секунды на обращение.
Повторный разбор кэшируется в базе и не тратит вызовов.

**Почему YandexGPT, а не Qwen, который вы упоминали?**
Мы замерили обе. Qwen3 на 235 миллиардов параметров отвечал 28 секунд,
YandexGPT-5-Pro — 0,9 секунды при лучшем русском. Qwen доступен в том же
каталоге и включается сменой одной строки в настройках.

**Вы дообучали модель?**
Нет. Вместо этого в промпт заложена дисциплина работы с найденным контекстом:
отвечать только по фрагментам, не склеивать шаги из разных инструкций,
не распространять частный случай на общий, переписывать значения буквально.
Это даёт основной эффект без данных и без времени на обучение.

**Чем вы отличаетесь от готовых решений вроде встроенного ИИ в системах заявок?**
Мы не заменяем систему заявок, мы закрываем участок между входящим текстом и заведённой
заявкой. Это то место, где сейчас сидит человек и делает ручную работу.

**Вы использовали ИИ при написании кода?**
Да, это разрешено правилами. Архитектуру, контракт API и промпты проектировали сами,
код писали с ассистентом.

## README репозитория

Это оценивается. Собери к 16:30.

Обязательные разделы: что это и для кого, скриншот главного экрана, три шага запуска,
`.env.example` с пояснением, откуда взять ключ, схема из пяти шагов агента текстом,
описание где LLM а где код, ограничения, состав команды.

Шаги запуска должны работать на чистой машине:

```bash
git clone <ссылка>
cd ShortHack

# бэкенд
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # вписать LLM_API_KEY, либо оставить LLM_PROVIDER=mock
uvicorn app.main:app --reload

# фронтенд, во втором терминале
cd frontend
npm install
npm run dev
# открыть http://localhost:5173
```

Обязательно припиши: «Без ключа модели приложение запускается в демонстрационном режиме
на заглушке, весь сценарий работает». Это спасает, если жюри не сможет подставить ключ.
