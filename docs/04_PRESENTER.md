## Продуктовая рамка

Это то, что ты должен уметь сказать без слайдов.

**Пользователь.** Оператор первой линии технической поддержки. Не конечный сотрудник.
Это принципиально: мы не делаем ещё одного чат-бота, который раздражает людей. Мы ускоряем
работу человека, через которого проходит весь поток.

**Боль.** Обращения приходят почтой и звонками. Люди описывают проблему своими словами,
пропускают важные детали, задают три вопроса в одном письме. Оператор каждый раз вручную
вчитывается, достаёт из текста логин и код ошибки, решает, куда это отнести и что делать
дальше. Это однообразная работа, которая занимает большую часть его времени и на которой
он ошибается к концу смены.

**Решение.** SupportPilot разбирает обращение, достаёт из него структуру, находит похожие
уже решённые заявки и сам выполняет следующий шаг: заводит заявку, готовит уточняющий
вопрос или черновик ответа. Оператор проверяет и подтверждает одним кликом.

**Почему человек остаётся в контуре.** Модель может ошибиться. Поэтому агент не отправляет
письма и не закрывает заявки сам: он готовит, человек подтверждает. Это ответ на главный
вопрос жюри про доверие.

## Структура презентации

Одиннадцать слайдов. На 4 минуты это предел, больше не успеешь.

| № | Слайд | Что на нём | Сколько говоришь |
|---|---|---|---|
| 1 | Титул | Название, тэглайн «ИИ-помощник первой линии поддержки», команда | 5 сек |
| 2 | Пользователь и боль | Один оператор, поток обращений, три цифры боли | 30 сек |
| 3 | Что делает продукт | Одна фраза и три иконки: разобрать, найти, выполнить | 20 сек |
| 4 | **Демо** | Живой прогон или видео | **90 сек** |
| 5 | Как устроен агент | Схема пяти шагов | 40 сек |
| 6 | Где LLM, а где код | Две колонки | 25 сек |
| 7 | Человек в контуре | Скриншот кнопок подтверждения | 15 сек |
| 8 | Эффект | Расчёт экономии | 20 сек |
| 9 | Стек и запуск | Логотипы, две команды запуска | 10 сек |
| 10 | Ограничения и планы | Честный список | 20 сек |
| 11 | Контакты и ссылки | QR на репозиторий | 5 сек |

Демо занимает почти половину времени. Так и должно быть: жюри хочет увидеть работающий продукт,
а не услышать про него.

### Слайд 2, цифры боли

Подавай их как оценку команды, а не как факт из отчёта. Формулировка: «по нашей оценке».

- Оператор тратит на разбор одного обращения около 6 минут.
- Примерно 4 из 10 обращений приходят с неполными данными, и по ним нужен ещё один круг переписки.
- Около трети обращений — повторы уже решённых проблем.

### Слайд 5, схема агента

Пять блоков в строку, стрелки между ними. Подписывай, где работает модель, а где обычный код.

```
[ Обращение ]
      |
  1. Модель: разобрать текст в структуру
      |
  2. Код: найти похожие заявки
      |
  3. Код: найти статьи базы знаний
      |
  4. Модель: выбрать действие и вызвать инструмент
      |
  5. Код: выполнить инструмент
      |
[ Заявка / Уточнение / Черновик ответа ]  ->  [ Оператор подтверждает ]
```

Рисуй в Figma или прямо в редакторе презентаций фигурами. Не трать на это больше 25 минут.

### Слайд 6, где LLM, а где код

Это слайд, который любят технические жюри. Он показывает, что вы думали про стоимость и надёжность.

| Отдали модели | Оставили коду |
|---|---|
| Понять свободный текст на русском | Поиск похожих заявок по словам |
| Достать логин, код ошибки, устройство | Поиск по базе знаний |
| Определить категорию, приоритет, команду | Определение массового сбоя по счётчику |
| Понять, каких данных не хватает | Создание записей в базе |
| Выбрать следующий шаг | Смена статусов и маршрутизация |
| Написать письмо пользователю | Присвоение номера заявки |

Фраза для защиты: «Мы сознательно не зовём модель там, где хватает двадцати строк кода.
Это быстрее, дешевле и предсказуемее».

### Слайд 8, расчёт эффекта

Покажи формулу, а не голую цифру. Числа — это допущения команды, так и скажи.

```
Поток обращений на команду          120 в день
Ручной разбор одного обращения      6 минут
Разбор с помощником                 1,5 минуты (проверить и подтвердить)
Экономия на обращении               4,5 минуты
Экономия в день                     120 × 4,5 = 540 минут = 9 часов
В пересчёте на людей                примерно 1,8 ставки оператора
```

Обязательно добавь строчку: «Это оценка на наших допущениях, точные цифры зависят
от реального потока и доли сложных обращений». Жюри ценит честность гораздо выше красивой цифры.

### Слайд 10, ограничения и планы

Честный список выигрывает. Не прячь недостатки, жюри их всё равно найдёт.

**Ограничения прототипа**
- Локальный запуск, без развёртывания и без авторизации.
- Поиск похожих заявок по словам, без векторного поиска.
- База знаний из восьми статей, загружается из файла.
- Аудио звонков не обрабатываем, работаем с готовой расшифровкой.

**Что добавили бы дальше**
- Векторный поиск по всему архиву заявок вместо поиска по словам.
- Обучение на подтверждениях и правках оператора: чем чаще правят приоритет, тем точнее становится.
- Интеграция с реальной почтой и системой заявок.
- Автоматическое закрытие простых повторяющихся обращений после накопления статистики.

## Скрипт защиты на 4 минуты

Выучи первые и последние две фразы наизусть. Середину говори своими словами.

> **(0:00)** Добрый день. Мы сделали SupportPilot — помощник оператора первой линии поддержки.
>
> **(0:05)** Наш пользователь — не сотрудник, который пишет в поддержку, а оператор, который
> разбирает этот поток. Каждое обращение написано свободным текстом: человек пропускает логин,
> путает название сервиса, задаёт три вопроса в одном письме. Оператор вчитывается, достаёт
> детали руками, решает, куда отнести и что делать. По нашей оценке это около шести минут
> на обращение, и почти половина обращений требует ещё одного круга переписки.
>
> **(0:35)** SupportPilot делает этот разбор за оператора и сам выполняет следующий шаг.
> Покажу.
>
> **(0:55) ДЕМО.** Вот очередь обращений. Беру письмо про VPN. Нажимаю «Разобрать».
> Модель вернула структуру: суть, категория, приоритет с обоснованием, команда,
> и она достала из текста логин, код ошибки и операционную систему. Дальше система
> нашла две похожие закрытые заявки — вот их решения, оператор сразу видит, чем закончилось
> в прошлый раз. И агент уже создал заявку SD-1013 на сетевую команду. Я подтверждаю — готово.
>
> Теперь другое обращение. Здесь человек пишет «ничего не работает» и не оставил логин.
> Разбираю. Система видит, что данных не хватает, и вместо заявки готовит письмо
> с конкретными вопросами. Отправляю.
>
> **(2:25)** Вот как это устроено. Пять шагов. Модель работает на двух из них: разобрать текст
> и выбрать действие. Всё остальное — обычный код: поиск похожих, поиск по базе знаний,
> создание записей. Мы сознательно не зовём модель там, где хватает двадцати строк кода.
>
> **(3:00)** Действие агент выполняет по-настоящему, но подтверждает человек. Модель может
> ошибиться, поэтому письма не уходят сами и заявки не закрываются сами.
>
> **(3:20)** По нашим допущениям это экономит около девяти часов работы в день на команде,
> которая разбирает сто двадцать обращений.
>
> **(3:35)** Прототип локальный, поиск похожих по ключевым словам, база знаний из восьми статей.
> Дальше — векторный поиск по архиву и обучение на правках оператора.
>
> **(3:55)** Спасибо. Готов ответить на вопросы.

## Вопросы жюри и ответы

Подготовь их заранее, на них уходит вторая половина баллов.

**Что если модель ошибётся с приоритетом?**
Оператор видит обоснование приоритета и может поменять его прямо в карточке до подтверждения.
Исправление сохраняется, и это данные, на которых систему можно донастроить.

**Почему не отдали модели весь процесс целиком?**
Модель дорогая, медленная и недетерминированная. Поиск похожих заявок и создание записи
в базе — это детерминированные задачи, код делает их за миллисекунды и всегда одинаково.
Модель нужна там, где есть неоднозначный человеческий текст.

**Как боретесь с придуманными фактами?**
Промпт прямо запрещает достраивать данные, отсутствующие поля просто не попадают в ответ.
Всё, чего не хватило, модель обязана перечислить отдельным списком, и именно он превращается
в уточняющие вопросы. Плюс человек подтверждает результат.

**Что будет на объёме в тысячи заявок?**
Поиск по словам придётся заменить на векторный, это основной пункт наших планов.
Остальная архитектура не меняется: это обычное приложение с базой.

**Сколько стоит один разбор?**
Два вызова модели на обращение, вход около полутора тысяч токенов. Повторный разбор
одного и того же обращения кэшируется в базе и не тратит вызовов.

**Чем вы отличаетесь от готовых решений вроде встроенного ИИ в системах заявок?**
Мы не заменяем систему заявок, мы закрываем участок между входящим текстом и заведённой
заявкой. Это то место, где сейчас сидит человек и делает ручную работу.

**Вы использовали ИИ при написании кода?**
Да, это разрешено правилами. Архитектуру, контракт API и промпты проектировали сами,
код писали с ассистентом.

## README репозитория

Это оценивается. Собери к 16:30.

Обязательные разделы: что это и для кого, скриншот главного экрана, три шага запуска,
`.env.example` с пояснением, откуда взять ключ, схема из пяти шагов агента текстом,
описание где LLM а где код, ограничения, состав команды.

Шаги запуска должны работать на чистой машине:

```bash
git clone <ссылка>
cd ShortHack

# бэкенд
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # вписать LLM_API_KEY, либо оставить LLM_PROVIDER=mock
uvicorn app.main:app --reload

# фронтенд, во втором терминале
cd frontend
npm install
npm run dev
# открыть http://localhost:5173
```

Обязательно припиши: «Без ключа модели приложение запускается в демонстрационном режиме
на заглушке, весь сценарий работает». Это спасает, если жюри не сможет подставить ключ.
