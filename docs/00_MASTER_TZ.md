# Мастер-ТЗ: SaluteAgent

## 1. Что требует кейс

Дословно из презентации организаторов:

**Обязательный минимум.** Прототип должен уметь три вещи:
1. Принимать обращение — письмо или текстовую расшифровку разговора.
2. Использовать API LLM — для понимания обращения, подготовки данных или выбора следующего шага.
3. Предлагать и выполнять действие — хотя бы одно из: создать заявку, сохранить категорию, подготовить уточнение.

**Команда сама решает:** какие данные хранить в заявке, как показывать результат пользователю, где применять LLM, а где хватит обычной программной логики.

**Агентная часть.** Переход от анализа к действию. Инструментом может быть простая функция программы. Агентные платформы разрешены, но не обязательны.

**Что показать в конце:** кто пользователь и какую проблему решаем; где используется LLM и как её результат влияет на действия программы; что получилось, какие ограничения, что добавили бы дальше.

**Что не требуется:** реальные интеграции, обработка аудио, сложный дашборд, промышленная архитектура. Достаточно локального прототипа и краткой инструкции запуска.

## 2. Наш продукт

**SaluteAgent — рабочее место оператора первой линии поддержки.**

Пользователь продукта — **оператор техподдержки L1**, не конечный сотрудник. Это важно для защиты: мы не делаем чат-бота для пользователей, мы ускоряем работу человека, который разбирает поток обращений.

Сценарий целиком, один и законченный:

1. В инбоксе оператора лежит очередь обращений. Часть пришла почтой, часть — расшифровки телефонных звонков.
2. Оператор открывает обращение и нажимает «Разобрать».
3. За один прогон агент делает следующее.
   - LLM извлекает структуру: резюме, список отдельных вопросов внутри письма, категория, сервис, приоритет, ответственная команда, найденные сущности, чего не хватает.
   - Программная логика ищет похожие закрытые заявки и статьи базы знаний. Здесь LLM не нужна.
   - LLM выбирает и вызывает инструмент: создать заявку, запросить уточнение или подготовить черновик ответа.
   - Инструмент реально исполняется. Заявка появляется в базе со статусом «предложена».
4. Оператор видит карточку разбора, трассу шагов агента и результат. Жмёт «Подтвердить», «Изменить» или «Отклонить».
5. Заявка переходит в работу, обращение помечается обработанным.

Дополнительно, если останется время: экран повторяющихся проблем. Если за последние часы пришло три и более обращения одной категории по одному сервису, система поднимает флаг возможного массового инцидента.

## 3. Почему именно этот сценарий

Он закрывает все три пункта обязательного минимума и даёт понятную историю на защите. Приём обращения есть. LLM применяется дважды и в разных ролях: извлечение структуры и выбор действия. Действие реально выполняется через вызов инструмента. Человек остаётся в контуре, что снимает вопрос жюри про галлюцинации.

## 4. Стек

| Слой | Технология |
|---|---|
| Бэкенд | Python 3.11+, FastAPI, Uvicorn, Pydantic v2, SQLAlchemy 2 |
| База | SQLite, файл `backend/saluteagent.db` |
| LLM | HTTP-клиент на httpx, OpenAI-совместимый протокол, ключ от организаторов |
| Фронтенд | React 18, Vite, TypeScript, обычный CSS без UI-библиотек |
| Запуск | два процесса: `uvicorn` на 8000, `vite` на 5173, прокси `/api` |

Никаких Docker, Redis, Postgres, векторных баз и очередей. Всё лишнее режем.

## 5. Роли

| Роль | Кто | Зона ответственности |
|---|---|---|
| Разработчик A | бэкенд | FastAPI, SQLite, seed-данные, LLM-клиент, промпты, агент, поиск похожих, статистика |
| Разработчик B | фронтенд | React, инбокс, карточка разбора, трасса агента, заявки, дашборд |
| Третий | презентация | Продуктовая рамка, слайды, схема архитектуры, скрипт защиты, README, отправка промежуточных решений |

**Ключевой приём для параллельной работы.** Контракт API заморожен до написания кода и лежит в `docs/01_CONTRACT.md`. Разработчик B первые три часа работает на моках и не ждёт бэкенд ни минуты. Переключение на живой бэкенд — одна строчка в конфиге.

| 2 | 11:40–12:40 | ЧП-2 в 12:40, **сдаём промежуточное решение** | Первый живой вызов LLM возвращает структуру, карточка разбора отрисована, репозиторий публичный |
| 3 | 12:40–14:40 | ЧП-3 в 14:40, **сдаём промежуточное решение** | Агент вызывает инструменты и создаёт заявки, фронт подключён к живому бэкенду, сквозной сценарий работает |
| 4 | 14:40–17:00 | Финальная загрузка | Полировка, дашборд, README, презентация, репетиция, запасная запись демо |

## 8. Критерии готовности

Прототип считается готовым, когда выполняется всё перечисленное.

- [ ] `git clone`, две команды запуска, приложение открывается в браузере.
- [ ] В инбоксе видны 12 демо-обращений, среди них письма и расшифровки звонков.
- [ ] Кнопка «Разобрать» возвращает заполненную карточку меньше чем за 15 секунд.
- [ ] В карточке видно: резюме, категория, приоритет, команда, извлечённые данные, чего не хватает.
- [ ] Виден список шагов агента с названиями инструментов и временем каждого шага.
- [ ] Агент создал заявку, она видна в разделе заявок, статус меняется по кнопке.
- [ ] Для обращения с неполными данными агент выбрал уточнение, а не создание заявки, и сформулировал конкретные вопросы.
- [ ] Приложение не падает при отсутствии ключа LLM: включается запасной режим и это видно в интерфейсе.
- [ ] README содержит инструкцию запуска и `.env.example`.

## 9. Риски и что с ними делать

| Риск | Действие |
|---|---|
| Ключ LLM выдали поздно или он не работает | В клиенте с самого начала есть режим `mock`, который отдаёт заранее записанный ответ. Разработка не встаёт |
| Модель не поддерживает вызов инструментов | Запасной путь: второй вызов LLM с JSON-схемой `{action, arguments}`, дальше диспетчер на стороне Python. Переключатель `LLM_TOOLS=auto\|json` |
| Модель возвращает сломанный JSON | Функция `parse_json_loose`: вырезать блок между первой `{` и последней `}`, при неудаче один повторный вызов с требованием отдать только JSON |
| Медленные ответы модели | Таймаут 30 секунд, кэш разбора по `message_id` в таблице `analyses`, повторный запрос не дёргает модель |
| Слияния в git ломают работу | Ветки не заводим. `main`, коммиты часто, у каждого свои папки: A трогает `backend/`, B трогает `frontend/`. Пересечений нет |
| Не успели с дашбордом | Он последний в списке. Вырезается без ущерба для обязательного минимума |
